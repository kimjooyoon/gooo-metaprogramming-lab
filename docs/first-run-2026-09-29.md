# First IR transformation run — 2026-09-29

This is a single synthetic structural case, used to test the lab pipeline and
metric contract. It is not a model accuracy claim.

## Decision

The Korean payment task was sent through `gooo decide` to the local CPU Laya
multilingual checkpoint at revision
`55cf4c4ebb4ebe31b2550e8bdf3bd21b99753851`. On the 20 repeated identical
decision requests, Laya selected `keep_current` every time:

| Choice | Probability |
| --- | ---: |
| `keep_current` | 0.6468 |
| `decompose_payment_flow` | 0.3532 |

The receipt reported `confidence=0.0631` and
`answer_confidence=0.6468`. Treat these as recorded model outputs, not a
calibrated probability that the structure is complete.

## Structural result

The declared contract contains 20 atoms: 5 entity types, 4 activity names, and
11 input/output type occurrences.

| Candidate | IR valid | Generated Go compiles | Two-run output replay matches | Contract coverage |
| --- | --- | --- | --- | ---: |
| `keep_current` baseline | yes | yes | yes | 7/20 (35%) |
| Laya-selected `keep_current` | yes | yes | yes | 7/20 (35%) |
| Oracle `decompose_payment_flow` | yes | yes | yes | 20/20 (100%) |

The Laya-selected structure tied the baseline and sat 65 percentage points
below the best compiling candidate. The oracle result is an upper bound because
the evaluator already knows the fixture's structural contract. The contract is
not sent to Laya, but this one case cannot show that the model will choose the
better structure on other tasks.

The disconnected run selected `keep_current` with
`mode=deterministic_fallback` and `fallback_reason=NOT_CONFIGURED`. Its request
digest, IR digest, and generated Go digests matched the Laya-selected
`keep_current` candidate. Both candidates also matched their own second
generation replay byte-for-byte.

This result is evidence that the measurement pipeline distinguishes the
baseline, a model-selected transformation, and a measurable oracle ceiling. It
is also evidence that this zero-shot decision did **not** improve completeness.
Do not add this classifier to production code generation until a larger
Gooo-specific corpus shows a repeatable lift.

## Latency and CPU for this task

After the Laya server and both routed checkpoints were loaded, the exact
code-generation decision request was sent 20 times from the Gooo CLI on an
Apple M4 CPU host:

| Measure | Result |
| --- | ---: |
| Warm decision round trip p50 | 72.91 ms |
| p95 | 90.78 ms |
| Mean | 81.31 ms |
| Max | 230.99 ms |
| Laya process CPU during batch | 106.4% of one core on average |
| Laya process CPU time / batch wall time | 1.731 s / 1.627 s |
| Loaded Laya process RSS | about 565 MiB |

This request was longer than the small routing sample in the Gooo baseline,
whose p50 was 61.59 ms. The maximum is a single outlier; the 20 calls reuse the
same prompt, so they measure latency and stability, not accuracy.

The current Gooo billing projection has no workflow-control-flow edge or
business-function semantics for this fixture. Successful compilation confirms
only that the declarations and generated Go are structurally valid. Behavioral
completeness remains `NOT_SCORABLE`.
